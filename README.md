# Aafno Praman

**आफ्नो प्रमाण** — "your own proof."

Academic and employment credentials for Nepal, anchored to a public blockchain.
A university publishes a degree, the graduate confirms it, and any employer can
check it in seconds — without phoning the campus, and without trusting this
platform's word for it.

The thing being solved is specific. Verifying a Nepali degree today means a
physical visit to the issuing campus, a paper request, and a wait measured in
weeks. That cost is why most employers simply do not verify, and that is what
makes a forged transcript worth making.

## The four ideas that shape everything

**1. Nothing is published without the holder's consent.**
Issuing does not put a credential on chain. It creates an *offer*. The named
holder gets an email showing the exact fingerprint that would be published, and
only their acceptance moves the record to `PENDING_ANCHOR` and then `ISSUED`.
A university cannot publish a fact about a person who has not agreed to it —
the entire status machine exists to enforce that, and `test_consent_gate.py`
exists to keep it enforced.

**2. Only hashes go on chain. Never personal data.**
A blockchain is permanent and world-readable. Putting a citizenship number on
one is not a security decision, it is a permanent disclosure. What gets anchored
is a SHA-256 fingerprint of a canonical JSON payload, and the payload itself
stays in Postgres behind authorisation. The chain proves *this exact record
existed, unaltered, at this time, published by this issuer* — which is all a
verifier actually needs.

**3. Verification has seven answers, not two.**
`VERIFIED`, `TAMPERED`, `SUBJECT_MISMATCH`, `REVOKED`, `SUPERSEDED`,
`UNCONFIRMED`, `NOT_FOUND`. A recruiter must be able to tell "this document was
altered" from "the university withdrew this degree" from "our node is briefly
unreachable." Collapsing those into a red cross would accuse honest graduates of
forgery every time an RPC endpoint hiccuped.

**4. Nobody is asked to hold a private key for their own credentials.**
Signing keys are *custodial* — generated by the platform when the registrar
approves an organisation, encrypted at rest with Fernet, and used server-side.
A university registrar cannot be asked to safeguard a seed phrase whose loss
permanently ends their ability to issue degrees, and a graduate cannot be asked
to install a browser extension to accept their own diploma.

## How a credential travels, end to end

```
  REGISTRAR                INSTITUTION              GRADUATE            EMPLOYER
      │                         │                       │                   │
      │ approves the college    │                       │                   │
      ├────────────────────────►│                       │                   │
      │  · generates a keypair  │                       │                   │
      │  · encrypts the key     │                       │                   │
      │  · registers on chain   │                       │                   │
      │  · funds it with gas    │                       │                   │
      │                         │                       │                   │
      │                         │  issues a degree      │                   │
      │                         ├──────────────────────►│  status: OFFERED
      │                         │                       │  ← nothing on chain yet
      │                         │                       │
      │                         │      accepts          │
      │                         │◄──────────────────────┤  status: PENDING_ANCHOR
      │                         │                       │         ↓
      │                         │                       │  anchorRecord(hash)
      │                         │                       │  status: ISSUED
      │                         │                       │
      │                         │                       │  shares a link   │
      │                         │                       ├─────────────────►│
      │                         │                       │                  │
      │                         │                       │   uploads the PDF│
      │                         │                       │   ┌──────────────┤
      │                         │                       │   │ hash it
      │                         │                       │   │ find the record
      │                         │                       │   │ compare to chain
      │                         │                       │   └──► VERIFIED
      │                         │                       │        + tx hash
      │                         │                       │        + both hashes
      │                         │                       │
      │                         │  the graduate sees who checked, and when
      │                         │                       │◄─────────────────┘
```

The two places this deliberately refuses to proceed:

- **Approving an organisation** when the chain is unreachable. Approving it in
  the database alone produces an issuer that looks active in the UI and gets an
  opaque revert on its first issuance.
- **Reinstating a suspended one**, for the same reason.

Everything else degrades gracefully: with the chain down, issuing and consent
keep working, records wait in `PENDING_ANCHOR`, a banner appears on the
dashboards, and `manage.py anchor_pending` drains the backlog when the node
returns.

## Backend, app by app

### `apps/accounts` — who someone is

| File | What lives here |
|---|---|
| `models.py` | `User` (email as username, four roles), `SeekerProfile`, `IdentityLevel` |
| `identity.py` | HMAC and Fernet for citizenship numbers |
| `services.py` | `get_or_create_account`, `attest_citizenship` |
| `views.py` | Login, refresh, register, `/auth/me/`, password change |
| `signals.py` | Creates a `SeekerProfile` on every seeker `User` |

Roles: `SEEKER` (a citizen), `ORG_MEMBER` (institution or employer staff),
`REGISTRAR` (the platform).

**Citizenship numbers are never stored in the clear and never hashed plainly.**
Nepali citizenship numbers are district-structured and sequentially issued, so
the entire plausible keyspace can be walked — a plain SHA-256 of one is
reversible in seconds. They are stored as an HMAC under `NATIONAL_ID_PEPPER`
(for lookup) plus a Fernet ciphertext (for retrieval), which is why that pepper
has no default and the app will not boot without it.

### `apps/organizations` — who may issue

| File | What lives here |
|---|---|
| `models.py` | `Organization`, `OrganizationMembership`, `Subscription`, `OrganizationDocument` |
| `keys.py` | Custodial keypair generation; Fernet encryption at rest |
| `services.py` | Approve / reject / suspend / reinstate, chain-first and atomic |
| `provisioning.py` | Registrar creates an account and hands back a temporary password once |
| `views.py` | `/organizations/me/…`, the plan switch, the directory |

Approval is **chain-first and atomic**: generate the keypair, register on chain,
fund it with gas, and only then mark the row approved. If the ledger is
unreachable the whole thing rolls back — see `test_issuer_approval.py`.

### `apps/credentials` — the records themselves

| File | What lives here |
|---|---|
| `models.py` | `CredentialRecord`, `AcademicDetail`, `ExperienceDetail`, `ExperienceClaim`, `IssuanceBatch` |
| `payloads.py` | Builds the canonical payload that gets hashed |
| `services.py` | Issue, revoke, supersede, batch |
| `confirmations.py` | The consent gate — tokens, acceptance, decline |
| `offer_views.py` | A signed-in holder's offers |
| `notifications.py` | The "is this you?" email |

Status machine:

```
OFFERED ──accept──► PENDING_ANCHOR ──anchored──► ISSUED ──revoke──► REVOKED
   │                                                │
   └──decline──► DECLINED                           └──reissue──► SUPERSEDED
   └──expire───► EXPIRED
```

### `apps/ledger` — talking to the chain

| File | What lives here |
|---|---|
| `client.py` | web3 wrapper: nonce handling, gas, receipts, timeouts |
| `canonical.py` | Deterministic JSON + the domain-separated hash |
| `services.py` | `anchor_record`, `register_issuer`, `fund_issuer`, `revoke` |
| `models.py` | `AnchorRecord` — tx hash, block, chain id |
| `management/commands/anchor_pending.py` | Drains the backlog after an outage |

### `apps/verification` — the answer a verifier gets

| File | What lives here |
|---|---|
| `services.py` | The seven-outcome decision, in one place |
| `document_views.py` | Upload a PDF → hash → verdict; meters quota, logs access |
| `views.py` | Lookup by reference, share links, quota, candidate search |
| `access_log_views.py` | What a citizen sees about who checked them |
| `models.py` | `VerificationLog`, `ShareLink`, `PassportAccessLog` |

### `apps/audit` — what happened

Append-only `AuditEvent` rows. Every approval, issuance, revocation, and
verification writes one. `views.py` exposes an organisation's own slice.

## The contract

`contracts/contracts/CredentialRegistry.sol`

```solidity
function registerIssuer(address issuer, string calldata name) external onlyRegistrar;
function suspendIssuer(address issuer, string calldata reason) external onlyRegistrar;

function anchorRecord(bytes32 recordHash) external onlyActiveIssuer;
function anchorBatch(bytes32[] calldata hashes) external onlyActiveIssuer;
function revokeRecord(bytes32 recordHash, string calldata reason) external;

function getAnchor(bytes32 recordHash) external view returns (Anchor memory);
```

Three properties the tests pin:

- **A suspended issuer's existing credentials stay verifiable.** Suspension
  stops new anchors. Retroactively invalidating every degree a university ever
  issued because of an administrative dispute would punish the graduates.
- **Only the anchoring issuer can revoke.** A university cannot revoke another
  university's degrees.
- **Registrar handover requires the incoming registrar to accept.** A one-step
  transfer to a mistyped address permanently bricks the registry.

## Worked examples

### 1. Issue a degree

```bash
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/login/ \
  -H 'Content-Type: application/json' \
  -d '{"email":"registrar@tu.edu.np","password":"AafnoPraman2026!"}' | jq -r .access)

curl -X POST localhost:8000/api/v1/credentials/issue/academic/ \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "subject_email": "sita.sharma@example.com",
    "subject_full_name": "Sita Sharma",
    "detail": {
      "registration_number": "TU-2078-4471",
      "degree_title": "Bachelor of Computer Engineering",
      "level": "BACHELORS",
      "major": "Computer Engineering",
      "graduation_date": "2023-09-14",
      "cgpa": "3.62"
    }
  }'
```

```jsonc
{
  "id": "bae1699f-…",
  "status": "OFFERED",              // not ISSUED — the graduate has not answered
  "record_hash": "9f2c…",           // the exact fingerprint she is shown
  "anchor": null                    // nothing on chain yet
}
```

### 2. The graduate accepts

```bash
curl -X POST localhost:8000/api/v1/credentials/offers/bae1699f-…/accept/ \
  -H "Authorization: Bearer $SITA_TOKEN"
```

```jsonc
{
  "status": "ISSUED",
  "anchor": {
    "tx_hash": "0x71c…",
    "block_number": 4211903,
    "chain_id": 11155111,
    "issuer_address": "0x9dD7…d627"
  }
}
```

That `tx_hash` is a real Sepolia transaction, linked to
`sepolia.etherscan.io` everywhere the UI shows it.

### 3. An employer verifies the PDF

```bash
curl -X POST localhost:8000/api/v1/verify/document/ \
  -H "Authorization: Bearer $HR_TOKEN" \
  -F document=@degree.pdf \
  -F claimed_name="Sita Sharma"
```

```jsonc
{
  "result": "VERIFIED",
  "reason": "The document matches the record anchored by Tribhuvan University.",
  "document_sha256": "e3b0…",
  "expected_hash":   "9f2c…",
  "computed_hash":   "9f2c…",       // recomputed here; a verifier can redo it
  "chain": { "tx_hash": "0x71c…", "block_number": 4211903 },
  "subject_match": "CONFIRMED"
}
```

Change one character in the PDF and the same call returns `TAMPERED` with the
two hashes side by side, so the mismatch *is* the finding.

### 4. Prove tamper-evidence without the API at all

```bash
cd contracts && npx hardhat run scripts/chain-proof.js --network localhost
```

Anchors a record, alters one character, and shows the hash diverge — against
the contract directly, with the backend switched off.

## Running it

Full instructions, demo accounts, and a five-minute walkthrough are in
**[RUNNING.md](RUNNING.md)**. The short version:

```bash
# 1. Chain — Sepolia
cd contracts && npm install
export DEPLOYER_PRIVATE_KEY=0x…          # funded from a Sepolia faucet
npm run deploy:sepolia                    # prints the contract address

# …or entirely locally, no faucet needed:
npm run node                              # terminal 1
npm run deploy:local                      # terminal 2

# 2. Backend
cd backend && python -m venv .venv && source .venv/bin/activate
pip install -r requirements/dev.txt
cp .env.example .env                      # fill the three REQUIRED secrets
#                                           + CHAIN_CONTRACT_ADDRESS from above
python manage.py migrate
python manage.py seed_demo
python manage.py runserver

# 3. Frontend
cd frontend && npm install
cp .env.local.example .env.local
npm run dev
```

`.env` has **no defaults** for `DJANGO_SECRET_KEY`, `KEY_ENCRYPTION_KEY` or
`NATIONAL_ID_PEPPER`, and the app will not boot without them. A predictable
`KEY_ENCRYPTION_KEY` makes every issuer's signing key recoverable; a predictable
pepper turns the citizenship lookup column into a searchable list of citizens.
A silent insecure default would be worse than a loud startup failure.

## Things worth knowing before you change anything

**`CANONICAL_DOMAIN_TAG` is still `"VERIDOCK-RECORD-V1"`, on purpose.**
It is hashed into every fingerprint already written to the ledger, and
re-derived by `chain-proof.js` when a verifier checks one independently.
Renaming it to match the new brand would make every credential issued before the
rename verify as `TAMPERED` — a cosmetic edit with the blast radius of a
forged-document accusation against every existing holder. It is a protocol
version, and the version has not changed.

**The Postgres role and database are still named `veridock`.**
Renaming those is a migration with downtime, not a string replacement, and the
name is not user-visible.

**The wallet gate is not the signer.**
`WalletGate` sits in front of the institution and employer consoles and requires
MetaMask on the configured network. It establishes *who is operating the
console*. It does not sign credentials — anchoring still goes out under the
organisation's custodial key, server-side. The gate copy says so explicitly,
because someone who believes their MetaMask account is what makes a degree valid
will draw exactly the wrong conclusion the first time they switch accounts.

Citizens and the registrar are deliberately outside the gate. Requiring a
browser extension to accept your own degree would exclude most of the people
this platform exists for.

**The free allowance is 50 lookups/month, defined in three places.**
`FREE_PLAN_MONTHLY_LOOKUPS` (settings), `Subscription.monthly_lookup_limit`
(column default), and `PLANS.COMMUNITY.monthlyLookups` (the pricing page). They
have drifted before — 15, 50, and 10 respectively — so `tests/test_plan_limits.py`
now pins the two the backend owns.

**`exactOptionalPropertyTypes` is on in the frontend.**
`prop?: T` and `prop: T | undefined` are different types under it. Optional props
are spread in (`{...(x ? { prop: x } : {})}`) rather than assigned `undefined`.

**The React Compiler lint rules are on.**
No `setState` synchronously inside an effect body, and no ref writes during
render. Where state genuinely must be seeded from the browser, it goes through a
lazy `useState` initialiser (`auth-context.tsx`) or a promise callback
(`wallet-context.tsx`).

**Colour never carries meaning alone.**
Each of the seven verification outcomes has an icon and a plain-language
sentence as well as a colour — required for the ~8% of men with colour vision
deficiency, and for anyone reading a printout in black and white.
